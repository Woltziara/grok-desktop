# 工作认识跨机器接续：实际入口与冲突处理

## 使用路径

在输入框旁打开“工作认识”，选择当前业务对象。没有对象时可以直接给一件事命名并创建；普通未指定请求仍然原文直通。点“导出当前这件事”，得到独立的 `.grok-wk.json` 文件；默认方向是主机导出已确认版本，另一台机器在同一入口点“接入另一台带来的版本”。传送文件由使用者选择已有可信通道；程序不复制账号、密码、OAuth、浏览器 profile、Grok 配置、工具凭据、项目文件或工作认识之外的对象。接续包自身可能包含业务文字，必须按业务资料保管。

导入先显示版本关系和差异，不立即改当前认识。原话的 ID、会话来源、待处理状态、模型推断/用户决定、纠正和撤回历史一并保留。相同文本的不同来源不会折叠。接入后仍需使用者为当前会话选择这个业务对象，不把另一台机器的绑定、开关或探针设置强加到本机。

两边未分叉时允许明确确认后接续。两边都有独立更新时必须选择本轮按本机整版还是带来的整版继续；不会把矛盾判断自动拼成“共识”。选择形成包含双亲的版本节点，另一台随后能识别已经处理过的冲突。被选择之外的原件保存在备份和导入暂存文件中，可核对后逐条纠正。已包含的旧版不能回退新的纠正或复活撤回。

## 实现与恢复

版本关系绑定完整对象快照的 SHA-256 和父节点，不以 mtime、导出时间或机器时钟裁定正确性。文件完整性校验不是作者认证，也不是对业务判断真实性的证明；只接入可信来源。

对象仍使用现有 JSON/JSONL 文件，额外 `sync.json` 记录传输版本关系与导入代次。原生 Grok memory 不迁移、不改名合并。旧对象首次导出时补足空提交日志并建立初始检查点，保留既有语义。

替换前保存原件，暂存副本和日志位于工作认识独立 root 下的 `transfer-staging/`、`transfer-backups/`、`transfer-journals/`；待选包在 `transfer-incoming/`，关闭界面或重启仍可重新查看。替换中断时普通对象读取/列举按日志恢复；出现另一个本机版本或校验不符则保留两边并停止，不静默挑一边。未知用户文件不导出，但本机原件替换时保留。预览后本机又更新会拒绝旧预览提交并要求重新核对。导入更换对象代次，导入前在运行的旧 ACP 回合不能迟到写回新对象。

回滚原件时先退出两端应用，静止备份整个工作认识 root；核对 UI 报出的 backup 路径。恢复对象应同时恢复其六份对象/记录/inbox/commit/current/sync 文件，不用 mtime 覆盖另一个活跃应用。更安全的日常回退是重新导出当前版，在“工作认识”中明确纠正或撤回，而不是向活跃数据目录拷文件。
